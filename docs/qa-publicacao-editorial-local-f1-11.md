## Prova automatizada da implementação

`NewsPublishedPortalTest` verifica versão aprovada durante revisão pendente, audiência legível sem destinatários, exclusão de rascunhos e publicações alheias da pesquisa e contagem, ausência de excepção do autor/editor, datas UTC inclusivas, ordenação antes da paginação e filtros inválidos antes de ler qualquer fonte. `NewsPublishedRenderingTest` renderiza o detalhe e verifica escape do texto, autor, data e ligações de media privados. `NewsPublishedHttpTest` executa o controlador real num servidor PHP loopback descartável com runtime fechado e confirma 404 vazio privado antes de um redireccionamento posterior, incluindo métodos errados, arrays e página errada, além da cache privada no início/lista. Usa adaptadores mínimos de página, sem base de dados, e não substitui o WordPress integral. O ensaio SQL exclusivo `tests/integration/news-editorial.php` verifica as projecções sobre o repositório real com as suas próprias contas e tabelas, incluindo alteração de audiência num rascunho e remoção por arquivo. Conserva as provas de concorrência e rollback existentes.

Os comandos de referência são `npm test`, `npm run lint`, `npm run build`, `npm run test:php`, `npm run lint:php`, `npm run test:news:integration`, `npm run test:news-editorial:integration`, `npm run test:news-editorial-installer:integration` e `npm run test:news-editorial-upgrade:integration`. Sem Docker, PHP local e o WordPress CLI privado podem executar os mesmos testes de laboratório. Isso não prova os bindings wp-env nem a compatibilidade com IIS/MySQL.

A implementação passou 55 testes Node com Node 24.21.0, lint/build e as integrações exclusivas de submissão 49, editorial 59 e instalador 26, além do upgrade auditado. A reparação final `e2a4c58` passou 733 testes PHP e 2818 asserções no PHP 8.4.26 local, com quatro omissões de symlinks do Windows e sem depreciações. PHPCS passou nos sete ficheiros alterados. A job PHP Ubuntu desse SHA executou 733 testes e 2822 asserções, sem omissões. As duas workflows desse SHA e o check GitGuardian passaram. A integração continua dependente da revisão das correcções e dos checks no SHA final com a documentação. O ensaio positivo do instalador/upgrade de concessões foi local. Nos dois jobs de notícias em development, o instalador tem uma prova negativa de nove verificações e o upgrade fecha no gate. Não confundir estes resultados.

Na comparação de CAS antigo, a primeira igualdade de todas as linhas detectou uma alteração de `session_tokens` da conta técnica administradora. O diagnóstico por hashes de cada linha e dos campos de sessão isolou apenas `arn_oidc_last_seen`, actualizado pela actividade Google já existente. O token, expiração, geração e restantes campos não mudaram. O ensaio controlado normalizou apenas esse campo em memória para a comparação. Conservou todos os restantes campos administrativos e todas as sessões fictícias. Os dados brutos ficaram privados. Não se alega igualdade byte a byte de toda a metainformação de sessões nesse ensaio específico.

As rotas WordPress nativas têm semântica diferente do detalhe privado. REST sem nonce devolveu 401. Com nonce REST obtido pelo AJAX nativo e a sessão fictícia actual, o tipo privado devolveu 403 e a colecção inexistente 404. A query nativa do CPT devolveu 404 e o editor nativo 403. Nenhuma destas respostas revelou os títulos das publicações. O ficheiro da comunicação individual também devolveu 404 a B. Antes da correcção do aviso, o destino CMS devolvia 200 com Pedido de notícias indisponível, sem título. O defeito era de navegação e foi corrigido no destino do aviso sem alargar acesso ao CMS.

O foco usa a regra CSS de 3 px. Este Chromium no Windows devolveu 2,4 px computados. Um controlo isolado com outline e border de 3 px reproduziu os mesmos 2,4 px, enquanto largura e altura de 44 px mediram 44 px. O foco era visível no salto para conteúdo e nos campos CMS. Esta execução não comprova 3 px efectivos nem zoom nativo. Revalidar numa aceitação gráfica do ambiente homologado sem alterar a regra com base nesta quantização local.

Os primeiros helpers tiveram expectativas corrigidas antes de se aceitar resultados: nome do botão de arquivo, necessidade de destaque obrigatório, redireccionamento nativo 302 e distinção de REST com ou sem nonce. Uma navegação CMS ultrapassou o tempo de load com ensaios paralelos e foi repetida em domcontentloaded. Não se contam estas tentativas falhadas como provas positivas. As evidências e capturas ficam apenas no laboratório ignorado pelo Git.
